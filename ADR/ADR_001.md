## Contexto
Com o objetivo de padronizar, auditar e versionar a infraestrutura, decidiu-se por implementar Infraestrutura como Código (IaC) utilizando o Terraform para gerenciar recursos do provedor da AWS. O cenário proposto tem objetivo de possiblitar os seguintes items:

1. Construção de uma **Service Account** e **bucket S3** para armazenamento remoto do Terraform state.
2. Cosntrução de um **repositório central de IaC** para controle e versionamento de recursos como usuários, service accounts e recursos/componetes da AWS.
3. Criação de **contas de usuário para desenvolvedores** com permissões restritas aos serviços EC2 e RDS, organizadas via **grupos de IAM**.

## Decisão

### 1. Armazenamento de `terraform state`
- Será criado um **bucket S3** específico para armazenar os arquivos de state do Terraform com versionamento habilitado.
- A autenticação será feita através de uma **IAM Role (Service Account)** com políticas limitadas ao acesso de leitura/escrita ao bucket de state.
- O bloqueio de estado será feito com **DynamoDB**, evitando execução simultânea.

```hcl
# Exemplo de Terraform para backend
terraform {
  backend "s3" {
    bucket         = "terraform-state-bucket"
    key            = "global/financial/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}
```

### 2. Repositório de Infraestrutura como Código (IaC)

- Um repositório Git chamado infra-as-code será criado para conter todos os módulos Terraform organizados por tipo de recurso:

    users/
    iam_roles/
    service_accounts/
    networking/
    compute/

- O repositório será o ponto centralizado apra facilitar a governança e compliance.

### 3. Gerenciamento de Usuários e Permissões

- Cada desenvolvedor terá uma IAM User provisionada via Terraform, com autenticação via AWS CLI ou Console.

    Os usuários serão adicionados a grupos como:

      developer-ec2 → Acesso completo a EC2 (launch, stop, describe, terminate)

      developer-rds → Acesso limitado a RDS (describe, snapshot, monitoramento)

    As permissões devem ser controladas com IAM Policies gerenciadas e IAM Groups.

    #### Bloco de exempo para criação de usuário e grupo
    ´´´hcl
      resource "aws_iam_user" "dev_user" {
        name = "dev.joao"
      }

      resource "aws_iam_group" "ec2_group" {
        name = "developer-ec2"
      }

      resource "aws_iam_group_policy_attachment" "attach_policy" {
        group      = aws_iam_group.ec2_group.name
        policy_arn = "arn:aws:iam::aws:policy/AmazonEC2FullAccess"
      }

      resource "aws_iam_user_group_membership" "group_membership" {
        user = aws_iam_user.dev_user.name
        groups = [
          aws_iam_group.ec2_group.name
        ]
      }
    ```

### Justificativa

A escolha pela utilização do Terraform como ferramenta de Infraestrutura como Código (IaC) e a adoção de um repositório centralizado segue as boas práticas de gestão moderna de infraestrutura em nuvem, com foco em padronização, rastreabilidade e segurança.

A implementação proposta atende diretamente às necessidades encontradas, pois:

  - Garante versionamento e futura auditoria das alterações na infraestrutura por meio do uso de controle de versão (Git) e armazenamento remoto do estado do Terraform.

  - Centraliza a gestão de recursos sensíveis, como usuários, service accounts e outros componentes da AWS, promove maior consistência e a reutilização de código.

  - Facilita a colaboração, uma vez que o uso do backend remoto (S3) permite que múltiplos usuários trabalhem de forma segura sobre os mesmos recursos.
  - Aplica o princípio do menor privilégio, ao provisionar contas de "developer" com acesso restrito via grupos de IAM, reduz os impactos de possiveis ataques e erros operacionais.

  - Escala de forma sustentável, permitindo a criação de novos ambientes e recursos com mínima duplicação de esforço e maior governança, evitando DRY (Don't Repeat Yourself).

### Alternativas Consideradas

Uso de scripts shell ou AWS CLI não estruturados
- Não foram consideradas, embora ofereçam algum nível de automação, não atendem à complexidade e escalabilidade necessária, além de dificultarem a manutenção e reuso.

Outras ferramentas de IaC como Pulumi ou AWS CDK
- Não foram consideradas, a equipe optou por utilizar Terraform visto que o intuito é o aprendizado desta, e por possuir uma comunidade com maior suporte é mais ampla documentação, o que esperamos é reduzir a curva de aprendizado e acelera a implementação.

AWS Console
- Descartado, desde o principio, pois o foco é o versionamento, padronização nem rastreabilidade, além do que o AWS console pode dificultar a colaboração.

### Consequências

#### Prós

- **Segurança aprimorada:** O acesso aos recursos será permitido com base no princípio do menor privilégio, reduzindo riscos de uso indevido.
- **Colaboração mais eficiente:** Com o Terraform gerenciamos o state remoto (armazenado em backend como S3 + DynamoDB, por exemplo) o que permite que múltiplos pessoas da equipe colaborem  de forma segura e controlada.
- **Auditoria e rastreabilidade:** As mudanças na infraestrutura ficam versionadas, permitindo o rastreamento das alterações.
- **Reutilização e padronização:** A adoção de uma arquitetura modular com repositório central de Infraestrutura como Código (IaC) favorece a padronização entre projetos e acelera a construção de novos ambientes.
- **Escalabilidade:** O uso de módulos facilita o crescimento da infraestrutura conforme a demanda vai aumentadno.

#### Contras

- **Curva de aprendizado:** Os aprticipantes podem precisar de tempo para se familiarizar com as práticas do Terraform, controle de state remoto e arquitetura em módulos.
- **Sobrecarga inicial:** O desenho e manutenção de módulos reutilizáveis exige um esforço inicial muito maior em comparação a scripts pontuais.
- **Dependência de ferramentas externas:** O uso de backends remotos (como S3, Terraform Cloud, etc.) introduz dependência de serviços externos para funcionamento correto da infraestrutura.
- **Gerenciamento de estados sensível:** Mau uso ou conflitos no state remoto podem causar problemas de sincronização ou inconsistência na infraestrutura.
- **Governança adicional:** Será necessário implementar políticas e controles adicionais para garantir o uso correto dos módulos e do repositório central.
